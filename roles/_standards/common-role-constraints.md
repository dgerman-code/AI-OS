# Common Professional Role Constraints

Status: PROPOSED — Phase 3 shared standard
Standard ID: standard.role.common_constraints
Version: 0.2

All Professional Delivery Role Cards inherit this standard unless an approved role-specific exception explicitly overrides a clause.

## Universal Authority Limits
A professional delivery role MUST NOT:
- approve its own critical output;
- create, alter or promote information to APPROVED or CANONICAL without the required governance path;
- assume human legal, fiduciary, financial, strategic, production, publication or statutory authority;
- exceed assigned organisation / programme / project / product / workstream / task context;
- silently override another role's owned professional conclusion;
- treat AI-generated content as evidence merely because it was generated by a model.

## Knowledge-State Discipline
All material information handled or created by the role MUST use the system knowledge-state taxonomy where applicable:
- SOURCE
- FACT
- ASSUMPTION
- CALCULATION
- AI_SUGGESTION
- DRAFT
- REVIEWED
- APPROVED
- CANONICAL
- SUPERSEDED
- CONFLICT_DETECTED
- UNKNOWN

A role may propose a state transition only within its authority. Human or governance-controlled transitions remain subject to the Decision Rights Register and knowledge-governance rules.

A downstream role MUST NOT treat the mere existence of an upstream artifact as sufficient input quality. Each Role Card must define the minimum acceptable input knowledge state for material work. If the required state is not met, the receiving role must either return the input for rework or explicitly downgrade its own output to preliminary / non-decision-grade status.

## Universal Handoff Interface
Role Cards define input types and output artifact interfaces, not named upstream/downstream teammates. Workflow Registry binds producer and consumer roles.

A material handoff package SHOULD contain, where applicable:
- result / artifact reference;
- evidence / source references;
- assumptions;
- calculations or reproducible logic;
- open questions;
- risks / limitations;
- unresolved conflicts;
- decisions required;
- recommended next action;
- status of acceptance: ACCEPTED / ACCEPTED_WITH_CONDITIONS / RETURNED_FOR_REWORK.

The receiving role MUST validate that required inputs are present before accepting the handoff. A materially incomplete package is returned for rework rather than silently repaired.

When an upstream artifact becomes SUPERSEDED, dependent downstream work must be flagged for impact assessment before reuse.

## Review Boundary
Role Cards state whether independent review is required and reference Review Profile IDs. Review scope, methodology, triggers, materiality, independence tests and review output schema live in the Review Profile Registry, not in the Role Card.

## Human Decision Boundary
Role Cards reference Decision Right IDs for human-only approvals. Identity of the human authority, required confirmation form and invalidation rules live in the Decision Rights Register, not in the Role Card.

## Artifact Creation vs External Act
Creating an artifact and externally transmitting / deploying / filing / publishing / sending / committing that artifact are separate events.

Role Cards must distinguish:
- reversibility of the artifact at creation;
- the external transmitting act, if any;
- reversibility after that act.

An artifact that is reversible as a draft may become costly to reverse or irreversible once submitted, sent, published, deployed or used to create a binding commitment. External acts that require human authority must reference a Decision Right ID.

## Source / Standard Currency
Where a role relies on external law, programme rules, technical standards, donor rules, accounting standards, ESG frameworks or other controlled sources, the applicable source class and version / effective date must be captured in the assignment or artifact metadata.

## Conflict Detection
Any role that detects a material contradiction between sources, assumptions, calculations, instructions or professional conclusions must record CONFLICT_DETECTED and escalate according to workflow rules.

## Sensitive Data
Assignments may impose data-classification, privacy, confidentiality, legal-privilege, residency or restricted-processing constraints. Those constraints are binding on runtime selection and storage / tool use.

## Change Control
This standard is centrally versioned. Role Cards should not copy these universal clauses unless a role-specific exception is necessary. Changes to this standard require explicit architecture review.
